# Backend Architecture Design (Source of Truth)

This document is the **source of truth** for the `backEnd/` architecture in this repo.

- **Audience**: future AI models (and humans) making changes to `backEnd/`
- **Goal**: enforce a **modular, repeatable skeleton** (routes → middlewares → controllers → validators → services → models) with strict layer contracts
- **Important**: if the current codebase deviates from this document, **the AI should prefer aligning the code to this document** (within the scope of the task) rather than copying legacy patterns.

---

## Non‑negotiables (AI guardrails)

- **Barrel imports only**: prefer importing from `*_index.js` barrels (or `*.index.js` barrels) instead of deep file paths.
  - Examples observed: `backEnd/08_routes/_routes.index.js`, `backEnd/05_middlewares/_mddlwre.index.js`, `backEnd/00_config/_config.index.js`, `backEnd/03_services/_services.index.js`, `backEnd/06_models/_models.index.js`
- **Layer separation**:
  - **Routes** wire endpoints → middleware stack → controllers (no business logic).
  - **Controllers** are thin: call a service, then respond via `validRespond`, catch via `catch_errorHandler_cntrl`.
  - **Validators** validate + sanitize request data; they do **not** access the DB.
  - **Services** contain business logic and data access (Mongoose). They return a normalized result envelope.
  - **Helpers** (optional) contain reusable pure logic or small IO helpers used by services.
- **Normalized HTTP JSON envelope** (current runtime contract):
  - Success and failure responses are JSON shaped like:
    - `{ success: boolean, message: string, payload: any }`
  - Controllers should respond via `validRespond(...)` (observed in `backEnd/03_services/cntrl_returnHandler.js`).
- **Validation/sanitization middleware is the gate**:
  - Use `vld_sntzr_mddlwre(validatorFn)` in routes before controllers.
  - On success it may attach `req.body.sanitizedData`.
- **Modularity rule**:
  - Target **~170–200 lines per file** for most files.
  - **Exception**: foundational entry/registry files (e.g. `backEnd/server.js`, large barrel/index files) may exceed this if it improves readability.
  - When a service/helper grows: split into `*_helpers.js`, `*_utils.js`, or additional `*_srv.js` modules under a feature `_utils/` subfolder.
- **Directory density guideline**:
  - Prefer keeping directories to roughly **≤10 files**; once a folder becomes dense, split into subfolders (example: `brandServices_crud/`, `brandServices_sections/`, `brandServices_relations/`).

## Backend “spine” (entrypoint and lifecycle anchor)

### Canonical entry file

- **Anchor file**: `backEnd/server.js`
- Responsibilities:
  - Initialize Express app
  - Configure global middleware (security, parsing, session, i18n, static)
  - Mount feature routes under `/api/*`
  - Start listening after DB connect

### Request lifecycle (runtime flow)

```mermaid
flowchart TD
  A[HTTP request] --> B[Express app\nbackEnd/server.js]
  B --> C[Global middleware\nhelmet/cors/json/urlencoded/cookie/session]
  C --> D[i18n handler + middleware\n(backEnd/05_middlewares/_mddlwre.index.js)]
  D --> E[Route mount\nbackEnd/08_routes/*Routes.js]
  E --> F[Per-route middleware stack\n(e.g. auth_mddlwre, upload_mddlwre)]
  F --> G[vld_sntzr_mddlwre(validatorFn)\n-> sets req.body.sanitizedData]
  G --> H[Controller\n07_controllers/**/**_cntrl.js]
  H --> I[Service\n07_controllers/**/_utils/**Services/**_srv.js]
  I --> J[Mongoose models\n06_models/*.js]
  H --> K[validRespond(res, ...)\n03_services/cntrl_returnHandler.js]
  H --> L[catch_errorHandler_cntrl(res, ...)\n03_services/errorHandlers/catch_errorHandler_cntrl.js]
  K --> M[JSON response\n{success,message,payload}]
  L --> M
```

### Folder hop map (mental model)

```mermaid
flowchart LR
  R[08_routes] --> MW[05_middlewares]
  R --> C[07_controllers/<feature>Cntrl]
  C --> U[07_controllers/<feature>Cntrl/_utils]
  U --> V[.../_utils/<feature>Validators]
  U --> S[.../_utils/<feature>Services]
  U --> H[.../_utils/<feature>helpers]
  S --> M[06_models]
  C --> SV[03_services\n(validRespond/catch handlers)]
```

## Directory layout (what goes where)

Top-level directories currently present under `backEnd/`:

- **`00_config/`**: infrastructure configuration (DB, server, sessions, cookies, encryption, cloud storage config).
  - Barrel: `backEnd/00_config/_config.index.js`
- **`02_utils/`**: small shared utilities used across layers.
  - Example observed: `cleanupTempFile` exported via `backEnd/02_utils/utils.index.js`
- **`03_services/`**: cross-cutting backend services & response/error tooling (NOT feature business logic).
  - Response envelope: `validRespond` (controller response helper)
  - Error handling: `errorHandlers/` module + `catch_errorHandler_cntrl`
  - Auth helpers: JWT/password hashing, cookie helpers
  - Logger: `03_services/logger/`
  - Cloud storage adapters: `03_services/cloudStorage_srv/`
- **`04_helpers/`**: general helpers (repo-level utilities). (Use only when a helper is truly cross-feature.)
- **`05_middlewares/`**: Express middlewares (auth, upload, i18n, validation/sanitization).
  - Barrel: `backEnd/05_middlewares/_mddlwre.index.js`
- **`05_constants/`**: infrastructure/system constants (file sizes, provider enums, etc.).
  - Barrel (note spelling): `backEnd/05_constants/_constances.index.js`
- **`06_models/`**: Mongoose models.
  - Barrel: `backEnd/06_models/_models.index.js`
- **`07_controllers/`**: feature controllers + feature-local utils.
  - Structure is feature-based: `07_controllers/<feature>Cntrl/`
- **`08_routes/`**: Express routers (feature route registries).
  - Barrel: `backEnd/08_routes/_routes.index.js`
- **`09_validators/`**: shared validator primitives (cross-feature).
  - Use this for generic validators (email/phone/date/time/etc.)—not feature-specific validators.
- **`10_constances/`**: domain/business constants (project types, priorities, DB options, cloud storage options, etc.).
  - Barrel (note spelling): `backEnd/10_constances/_constances.index.js`
- **`i18n/`**: i18n configuration and initialization (used by `i18nHandler` export in middleware barrel).
- **`_logs/`**: application logs / diagnostics (non-source).
- **`scripts/`**: backend scripts.

### Naming + spelling conventions (observed & normalized)

This codebase currently uses both “**constants**” and “**constances**” in filenames:

- Observed barrels: `_constances.index.js` (in `05_constants/` and `10_constances/`)
- **Source-of-truth rule**: keep using the existing barrel filenames **as long as the codebase depends on them**.
  - If/when refactoring, prefer renaming to `constants` consistently, but do it as an intentional migration (not opportunistic).

## Feature folder skeleton (`07_controllers/<feature>Cntrl/`)

Each feature controller folder follows this shape (example: `settingsCntrl`, `brandCntrl`):

```

  <feature>Cntrl_crud/                     # CRUD controllers
    <feature>_add_cntrl.js
    <feature>_getAll_cntrl.js
    <feature>_getOne_cntrl.js
    <feature>_update_cntrl.js
    <feature>_delete_cntrl.js

  <feature>Cntrl_sections/                 # optional: section-style endpoints
    ...

  <feature>Cntrl_relations/                # optional: relationship endpoints
    ...

  _utils/
    <feature>Cntrl_utils.index.js          # utils barrel (exports validators/services/helpers)

    <feature>Validators/                   # feature validators
      <feature>Validators_crud/
      <feature>Validators_sections/
      <feature>Validators_relations/

    <feature>Services/                     # feature services (business logic)
      <feature>Services_crud/
      <feature>Services_sections/
      <feature>Services_relations/

    <feature>helpers/                      # optional: feature-local helpers
      _<feature>helpers.index.js
      <feature>_something_helpers.js
```

### Controller barrel pattern (observed)

- Example: `backEnd/07_controllers/brandCntrl/_brandCntrl.index.js`
  - Exports each controller as `default` under a named export.
- Example: `backEnd/07_controllers/settingsCntrl/_settingsCntrl.index.js`
  - Imports and re-exports the set of controllers for routes to consume.

### Feature utils barrel pattern (observed)

- Example: `backEnd/07_controllers/settingsCntrl/_utils/settingsCntrl_utils.index.js`
  - Exports services and validators from their directories.
- Example: `backEnd/07_controllers/brandCntrl/_utils/brandCntrl_utils.index.js`
  - Exports all `*_srv.js` and `*_vld.js` for that feature, grouped by concern.

## Routes layer (`08_routes/*Routes.js`)

### Responsibilities

- Define HTTP method + path structure
- Define middleware order
- Keep route files **wiring-only**

### Middleware order (canonical)

Order should generally be:

1. **auth** (when needed): `auth_mddlwre`
2. **upload** (when needed): `upload_mddlwre`
3. **validate + sanitize**: `vld_sntzr_mddlwre(feature_validator_fn)`
4. **controller**: `*_cntrl`

Observed example in `backEnd/08_routes/settingsRoutes.js`:

- `upload_mddlwre` → `vld_sntzr_mddlwre(settings_uploadLogo_vld)` → `settings_uploadLogo_cntrl`

## Middlewares (`05_middlewares/`)

### `vld_sntzr_mddlwre` (validation/sanitization gate)

**File**: `backEnd/05_middlewares/vld_sntzr_mddlwre.js`

Behavior contract:

- Receives a validator function `(req) => ({ isValid, message, sanitizedData })`
- If invalid:
  - Responds `400` with `{ success:false, message, payload }`
- If valid:
  - If `sanitizedData` exists, sets `req.body.sanitizedData = sanitizedData`
  - Calls `next()`
- If validator throws:
  - Responds `500` with `{ success:false, message:'Internal Server Error', payload:null }`

**Source-of-truth rule**: feature validators MUST return `{ isValid, message, sanitizedData }` (see next section).

## Validators (feature-local and shared)

### Validator contract (source of truth)

Every validator function used by `vld_sntzr_mddlwre(...)` must resolve to:

```js
{
  isValid: boolean,
  message: string,
  sanitizedData: any | null
}
```

Notes:

- **`message`** is the canonical field name (observed in `vld_sntzr_mddlwre` and feature validators like `settings_uploadLogo_vld`).
- Some legacy helpers return `{ msg }` as well (see `backEnd/03_services/validator_returnHandler.js`).
  - **Conformance rule**: if you use legacy helpers, ensure the final object still includes `message`.

### Sanitization rule

- Validators are expected to **sanitize** input and return the sanitized result as `sanitizedData`.
- Controllers/services should read sanitized data from:
  - `req.body.sanitizedData` (preferred)
  - `req.params` / `req.query` can be sanitized too, but keep a consistent pattern per feature.

## Controllers (thin orchestration)

### Controller responsibilities

- Read from request (prefer sanitized fields)
- Call a **single** service function for business logic
- Return the response through `validRespond`
- In `catch`, return `catch_errorHandler_cntrl`
- Use `finally` only for cleanup that must always run (example: temp-file cleanup after uploads)

### Controller → service contract (source of truth)

Services return:

```js
{ success: boolean, message: string, data: any }
```

Controller then does:

- `return validRespond(res, isDebug, displayName, success, message, data);`

### Response envelope (runtime)

**`validRespond`** (observed in `backEnd/03_services/cntrl_returnHandler.js`) returns:

```js
res.status(success ? 200 : 400).json({
  success,
  message,
  payload: data
});
```

### Error handling (controller level)

- Controllers should catch and call:
  - `catch_errorHandler_cntrl(res, displayName, isDebug, error)`
- The error handler may add a `debug` object in debug mode (stack + originalMessage).

---

## Services (business logic)

### Service responsibilities

- Implement business logic
- Interact with DB (Mongoose models from `06_models/`)
- Use feature helpers (if needed) for reusable logic
- Return the normalized service envelope

### Logging convention (observed)

Many services use:

- `[STARTED]` at top of function
- `[COMPLETED]` in `finally`

Source-of-truth rule:

- Keep the `[STARTED]`/`[COMPLETED]` pattern for long/important service operations.
- For tiny services, keep logs minimal (but consistent).

### Error handling in services (observed vs target)

Observed helper:

- `catch_errorHandler_service(name, isDebug, error)` (currently re-throws `new Error(...)`).

Source-of-truth guideline:

- Prefer throwing **typed AppErrors** (from `03_services/errorHandlers`) for consistent status codes.
- If you return `{ success:false, message, data:null }` instead of throwing, that is acceptable when the error is part of expected control flow (but keep it consistent per feature).

---

## Models (`06_models/`)

### Responsibilities

- Define Mongoose schemas and model exports
- Keep schema logic local; prefer business logic in services (not in models) unless it is truly schema-centric (virtuals, hooks that enforce invariants).

### Model barrel

Use `backEnd/06_models/_models.index.js` to import models.

## “Where does this code belong?” (decision tree)

Use this when adding/modifying backend behavior:

```text
Need an endpoint? → 08_routes/<feature>Routes.js
Need auth/upload/i18n/validation gating? → 05_middlewares/
Need to orchestrate request → service + respond? → 07_controllers/<feature>Cntrl/**_cntrl.js
Need to validate/sanitize request inputs? → 07_controllers/<feature>Cntrl/_utils/<feature>Validators/**_vld.js
Need business logic / DB operations? → 07_controllers/<feature>Cntrl/_utils/<feature>Services/**_srv.js
Need reusable helper logic within a feature? → 07_controllers/<feature>Cntrl/_utils/<feature>helpers/
Need cross-feature helper? → 02_utils/ (small) or 04_helpers/ (bigger)
Need infrastructure enums/constants? → 05_constants/
Need domain/business constants? → 10_constances/
Need shared primitive validators? → 09_validators/
```

## Canonical templates (copy/paste skeletons)

These are templates you should follow. They are intentionally “generic”, but aligned with observed conventions.

### Route template (`08_routes/<feature>Routes.js`)

```js
import express from "express";

import {
  auth_mddlwre,
  vld_sntzr_mddlwre,
} from "../05_middlewares/_mddlwre.index.js";
import {
  feature_action_cntrl,
} from "../07_controllers/featureCntrl/_featureCntrl.index.js";
import {
  feature_action_vld,
} from "../07_controllers/featureCntrl/_utils/featureCntrl_utils.index.js";

const router = express.Router();

router.post(
  "/:id/action",
  auth_mddlwre,
  vld_sntzr_mddlwre(feature_action_vld),
  feature_action_cntrl,
);

export default router;
```

### Controller template (`07_controllers/<feature>Cntrl/<feature>Cntrl_crud/<feature>_action_cntrl.js`)

```js
import { feature_action_srv } from "../_utils/featureServices/feature_action_srv.js";
import {
  catch_errorHandler_cntrl,
  validRespond,
} from "../../../03_services/_services.index.js";

const displayName = " | feature_action_cntrl.js | ";

const feature_action_cntrl = async (req, res) => {
  const isDebug = true;

  try {
    const { success, message, data } = await feature_action_srv(req, isDebug);
    return validRespond(res, isDebug, displayName, success, message, data);
  } catch (error) {
    return catch_errorHandler_cntrl(res, displayName, isDebug, error);
  }
};

export default feature_action_cntrl;
```

### Validator template (`07_controllers/<feature>Cntrl/_utils/<feature>Validators/**/<feature>_action_vld.js`)

```js
const displayName = " | feature_action_vld.js | ";

export const feature_action_vld = async (req) => {
  const body = req.body || {};

  if (!body) {
    return { isValid: false, message: `${displayName}missing body`, sanitizedData: null };
  }

  // TODO: sanitize/normalize values here
  return {
    isValid: true,
    message: "OK",
    sanitizedData: {
      // ...clean values
    },
  };
};
```

### Service template (`07_controllers/<feature>Cntrl/_utils/<feature>Services/**/<feature>_action_srv.js`)

```js
import { catch_errorHandler_service } from "../../../../03_services/_services.index.js";
import { SomeModel } from "../../../../06_models/_models.index.js";

const displayName = " | feature_action_srv.js | ";

export const feature_action_srv = async (req, isDebug) => {
  isDebug && console.log(`▄︻デ══━一💥${displayName}[STARTED]`);

  try {
    const { sanitizedData } = req.body || {};

    // Business logic + DB IO
    const doc = await SomeModel.findById(sanitizedData.id);

    return { success: true, message: "OK", data: doc };
  } catch (error) {
    return catch_errorHandler_service(displayName, isDebug, error);
  } finally {
    isDebug && console.log(`🏁${displayName}[COMPLETED]`);
  }
};
```

## Conformance notes (how to handle mismatches)

When you (human or AI) see mismatches between code and this document:

- **Prefer this doc** as the target skeleton.
- Make changes **incrementally**:
  - When touching a feature, align *that feature* to the skeleton.
  - Avoid refactoring unrelated features unless necessary.
- Keep behavior stable: update internals without breaking public API shape (`{ success, message, payload }`).

---

## Quick checklist: adding a new backend feature (minimal)

1. Create `08_routes/<feature>Routes.js` and export it from `08_routes/_routes.index.js`
2. Mount it in `backEnd/server.js` under `/api/<feature-plural>`
3. Create `07_controllers/<feature>Cntrl/` with:
   - `_<feature>Cntrl.index.js` barrel
   - `<feature>Cntrl_crud/` controllers
   - `_utils/<feature>Cntrl_utils.index.js` barrel
   - `_utils/<feature>Validators/...` validators
   - `_utils/<feature>Services/...` services
4. Enforce middleware order in routes: auth → upload → validate/sanitize → controller
5. Keep files modular (~170–200 lines target) and split by concern if growing
