# Frontend Architecture Design (Source of Truth)

This document is the **source of truth** for the `frontEnd/` architecture in this repo.

- **Audience**: future AI models (and humans) making changes to `frontEnd/`
- **Goal**: enforce a **modular, repeatable frontend skeleton** so you can say **WHAT** to build and the AI uses this doc for **HOW** to build it.
- **Important**: if the current codebase deviates from this document, the AI should **prefer aligning the code to this document** (within the task scope) rather than copying legacy patterns.

---

## Non‑negotiables (AI guardrails)

- **Plain JS/JSX only**: no TypeScript.
- **Context API only**: no Redux/Zustand.
- **Every user-visible string** uses i18n (`useTranslation`) and has keys in **all 4 locales**:
  - `frontEnd/public/locales/{en,ar,ru,hy}/`
- **No raw colors in component CSS**:
  - Use CSS variables defined in `frontEnd/src/09_styles/lightTheme.css` and `frontEnd/src/09_styles/darkTheme.css`
- **ClassName conventions** (strict):
  - **No `-` and no `__`** in your classNames.
  - Use **single underscores** only.
  - Root className is the **component name string**.
- **CSS location convention** (strict):
  - For page features built with the canonical page skeleton (see below), **all component CSS files live in that page’s `_styles/` folder**.
- **Barrel import convention**:
  - Prefer importing from `*.index.js` barrels (routes, contexts, page subfolders) rather than deep file paths.

## App “spine” (entrypoint and lifecycle anchor)

### Runtime entry

- `frontEnd/index.html` mounts `#root` and loads `src/main.jsx`
- `frontEnd/src/main.jsx` bootstraps React + loads i18n once
- `frontEnd/src/App.jsx` composes global providers + routing layouts

### High-level render flow

```mermaid
flowchart TD
  A[index.html] --> B[src/main.jsx\ncreateRoot().render(<App />)]
  B --> C[i18n init\nsrc/i18n/i18n.index.js]
  B --> D[App.jsx]
  D --> E[ThemeProvider → LanguageProvider → ProfileProvider]
  E --> F[React Router]
  F --> G[AdminLayout + AdminRoutes]
  F --> H[PublicLayout + PublicRoutes]
```

### Routing layout split (observed)

- `App.jsx` mounts:
  - `admin/*` → `AdminLayout` → `AdminRoutes`
  - `/*` → `PublicLayout` → `PublicRoutes`
- `AdminRoutes` uses lazy-loaded pages and protects parts via `ProtectedAdminRoutes`.

## Directory layout (what goes where)

`frontEnd/src/` contains:

- **`00_assets/`**: static assets (note: may include many lines due to bundled assets)
- **`01_components/`**: reusable components grouped by category (presentational/smart/state/styled/ui)
- **`02_context/`**: global contexts + hooks (Theme, Language, Profile, User)
  - Barrel: `frontEnd/src/02_context/context.index.js`
- **`03_config/`**: configuration (API endpoints, site settings, etc.)
  - Key: `frontEnd/src/03_config/apiEndpoints/adminEndpoints/ADMIN_endpoints.js`
- **`04_hooks/`**: shared hooks (cross-feature)
- **`05_helpers/`**: helper utilities (including API helper modules)
- **`06_routes/`**: router composition and layouts
  - `adminRouting/` and `publicRouting/` each have a barrel
- **`07_utils/`**: small shared utils
- **`08_constances/`**: domain constants (frontend)
- **`09_styles/`**: global styles and theme variables
  - `lightTheme.css`, `darkTheme.css`, plus global spacing/colors
- **`10_pages/`**: pages and feature UI (largest area)
- **`i18n/`**: i18n setup
- **`Test/`**: experimental/testing utilities (NOT the formal test framework)

## i18n (internationalization) — REQUIRED

### Initialization

- i18n is initialized once in `frontEnd/src/i18n/i18n.index.js`
  - Uses: `i18next-http-backend` + `i18next-browser-languagedetector` + `react-i18next`

### Rules

- Every component that renders user-visible text must get translation strings via:
  - `const { t } = useTranslation();`
- **Source-of-truth pattern** for pages:
  - Extract `t` in the **page’s main hook** (`useXXX.js`) and pass `t` down via `compProps` so leaf components do not call `useTranslation` repeatedly.

---

## Themes (dark/light) + CSS variables — REQUIRED

### Rules

- Global theme variables live in:
  - `frontEnd/src/09_styles/lightTheme.css`
  - `frontEnd/src/09_styles/darkTheme.css`
- Component CSS must use variables from those files (no raw colors).
- Feature-specific variables should be added under a clearly labeled block in both theme files.

## Global state (Context API only)

### Contexts (observed)

Global contexts are defined under `frontEnd/src/02_context/`:

- Theme (`themeContext/`)
- Language (`languageContext/`)
- Profile (`profileContext/`)
- User (`userContext/`)

### Provider composition (observed)

- `App.jsx`: `ThemeProvider → LanguageProvider → ProfileProvider → Router`
- `AdminLayout.jsx`: wraps with `UserProvider` (admin area gets auth/user state)

Source-of-truth rule:

- Keep contexts small and focused; do not build “god contexts”.
- Prefer page-local state in the page’s hook layer (see below).

## API endpoint config + API helper pattern (source-of-truth)

### Endpoint registry

All admin endpoints are defined in:

- `frontEnd/src/03_config/apiEndpoints/adminEndpoints/ADMIN_endpoints.js`

Each entry uses:

- `ENDPOINT` (string or function)
- `PROPERTIES` (object or function returning fetch options)
- `DISPLAY_NAME` (string for debugging/logging)

### API helper modules

API calls should be written as standalone helper modules under:

- `frontEnd/src/05_helpers/apiHelpers/...`

**Required return envelope** (frontend-normalized):

```js
return {
  success: body.success === true,
  message: body.message,
  data: body.payload ?? null,
};
```

Source-of-truth rule:

- Frontend always normalizes backend `{ payload }` into frontend `{ data }`.
- Always include `credentials: "include"` if the backend session cookie is required.

## Canonical Page Directory Architecture (MUST FOLLOW)

When creating a new page feature under `frontEnd/src/10_pages/`, you MUST follow this skeleton.

> Replace `XXX` with the **page directory name** (camelCase, starts lowercase), e.g. `adminProfile/`.
> Replace `YYY`, `ZZZ` with component “parts” (single underscore delimiters).

### Canonical tree (source of truth)

```text
frontEnd/src/10_pages/.../XXX/
  XXX.config.js
  XXX.jsx                      (Page parent component / entry point — PascalCase file name, e.g. AdminProfile.jsx)

  _styles/
    xXX.css
    xXX_YYY.css
    xXX_YYY_ZZZ.css

  01_XXX_comps/
    _XXX_comps.index.js
    XXX_YYY.jsx
    XXX_childComps/            (optional)
      _XXX_childComps.index.js
      XXX_YYY_ZZZ.jsx

  02_XXX_helpers/
    _XXX_helpers.index.js

  03_XXX_hooks/
    _XXX_hooks.index.js
    useXXX_states.js
    useXXX_apiHelpers.js
    useXXX_handlers.js
    useXXX.js

  04_XXX_vld/
    _XXX_vld.index.js

  05_XXX_cnst/
    _XXX_cnst.index.js

  06_XXX_memo/
    _XXX_memo.index.js

  07_XXX_test/
    _XXX_test.index.js
```

### Naming rules (strict)

#### Page directory name

- Page directory is **camelCase** and starts with lowercase:
  - ✅ `adminProfile/`
  - ❌ `AdminProfile/`

#### Component filenames

- Parent page component is `XXX.jsx` in the page root:
  - Example: directory `adminProfile/` → file `AdminProfile.jsx`
- Components used by the page are prefixed by the parent component name:
  - `AdminProfile_form.jsx`
- Child components carry full lineage:
  - `AdminProfile_form_fileSection.jsx`

#### CSS filenames + root className mapping (strict)

All CSS files for the page live in `_styles/`.

Rule: **CSS filename is the component filename, but with the first character lowercased**.

Examples (confirmed):

- Component: `AdminProfile.jsx`
  - CSS: `_styles/adminProfile.css`
  - Root className: `"AdminProfile"`
- Component: `AdminProfile_form.jsx`
  - CSS: `_styles/adminProfile_form.css`
  - Root className: `"AdminProfile_form"`
- Component: `AdminProfileForm.jsx`
  - CSS: `_styles/adminProfileForm.css`
  - Root className: `"AdminProfileForm"`

#### Internal classNames (strict)

- Root: `"ComponentName"` (exactly)
- Internal parts: `"ComponentName_partName"` (single underscore only)
- **Forbidden**: `-` and `__`

## The Page Hook Layer (MUST FOLLOW)

### Files and responsibilities

For page `XXX` (e.g. `AdminProfile`):

- `useXXX_states.js`
  - Declares all `useState`, `useRef`, setters.
  - Returns `{ states, setters, refs? }`
- `useXXX_apiHelpers.js`
  - Imports base API helpers from `frontEnd/src/05_helpers/apiHelpers`
  - Builds “polished wrappers” (optionally accepts global loaders/notifications)
  - Returns `{ apiHelpers }`
- `useXXX_handlers.js`
  - Defines all event handlers and action functions (typically using `useCallback`)
  - Returns `{ handlers }`
  - If it becomes large, split by concern:
    - Example: `useAdminProfile_handlers_form.js` that returns `{ formHandlers }`
- `useXXX.js` (main hook)
  - Orchestrates everything
  - Owns `useEffect` calls
  - Extracts `t` and passes it down
  - Builds `compProps` for each component

### compProps convention (strict)

Props objects must be named exactly:

- For component `AdminProfile_form`: `AdminProfile_form_props`
- For child component `AdminProfile_form_fileSection`: `AdminProfile_form_fileSection_props`

And passed like:

- `<AdminProfile_form {...compProps.AdminProfile_form_props} />`

## Route/feature code splitting (recommended)

- Use `React.lazy` for page-level modules (observed in `AdminRoutes.jsx`).
- Wrap routing with `Suspense` fallback at a high level (observed in `App.jsx`).

## Conformance notes (what to do when code differs)

- This doc is normative. When code differs, prefer updating the code to match the doc (within scope).
- Keep changes incremental:
  - When touching a page, align that page directory to the canonical skeleton.
  - When touching components, align CSS/className rules.
- Avoid “drive-by” refactors across unrelated pages.

## Simple static page structure exception

Not every page needs the full canonical page architecture.

If a page is **90–95% static content**, it should follow a simpler structure instead of the full page skeleton.

Examples:

- Privacy Notice
- Terms & Conditions
- FAQ
- Cookie Policy
- About page
- Simple legal/information pages
- Static policy pages

### Simple static page skeleton

```text
frontEnd/src/10_pages/.../privacyNotice/
  PrivacyNotice.jsx

  _styles/
    privacyNotice.css
